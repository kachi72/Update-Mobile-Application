# Plan 1-001 — Home and Category Redesign

## Summary

Implement the screenshot-led Figma redesign in the existing Java/XML Android application, beginning with the home experience and a reusable visual foundation for category screens.

## Context

- **Area:** Android UI / UX
- **Priority:** P1
- **Dependencies:** Existing Activities, Room article cache, category navigation, supplied redesign screenshots
- **Source:** User-supplied Figma screenshot and design direction
- **Target project:** `Update v2/Update`

## Implementation Plan

1. Establish the redesign color palette, surface colors, typography defaults, chips, navigation styling, and six reusable category gradient drawables.
2. Rebuild the home layout around a scrollable briefing screen with six large category cards, descriptions, source chips, cached article counts, and a persistent bottom navigation bar.
3. Update `MainActivity` to bind the redesigned views, preserve category navigation, and observe Room data so each card displays its cached article count.
4. Rebuild the offline category selector with the same card system and an offline-active bottom navigation state.
5. Update `OfflineActivity` to bind the redesigned navigation and expose cached article counts without performing network work.
6. Replace photographic backgrounds on every online and offline category screen with the gradient used by that category's home card.
7. Keep article fetching, Room storage, saved articles, and WebView behavior unchanged during this visual foundation phase.
8. Build the debug application, run local unit tests, and inspect resource/build failures before proceeding to later screenshots.

## Scope Decisions and Discrepancies

- The supplied screenshot is treated as the authoritative home-screen reference even though exact Figma measurements and tokens are unavailable.
- Category screen backgrounds use their matching home-card gradients because separate background artwork is unavailable.
- Article counts are derived from the existing Room cache rather than hard-coded screenshot values.
- The existing Help dialog is retained in code but is not part of the first screenshot's bottom navigation; it can be surfaced in a later settings/help design.
- Per user direction, no `changes` directory or change markdown files are created; implementation is applied directly.
